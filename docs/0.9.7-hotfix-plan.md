## HOTFIX-001: No-active-room route gate

- **Status**: done (2026-05-17)
- **Priority**: hotfix
- **Symptom**: When the signed-in user has no active room, the app
  shell (`AppLayout`) renders `ProjectSetup` (create/join) for
  *every* protected route. Routes that don't depend on an active
  room — most importantly `/archived-projects` (P1-004) and
  `/profile` — become unreachable. A user whose only project was
  just archived cannot reach the archived-projects page to restore
  it, and the browser URL silently lies (shows `/archived-projects`
  while rendering the setup screen).

### Suspected cause
- `src/pages/AppLayout.tsx:50-57` gates the `<Outlet />` on
  `activeRoom`. When `activeRoom` is null it short-circuits to
  `<ProjectSetup />`, regardless of the requested path. There is no
  allowlist for routes that should still render without a room.
- Result: `/archived-projects`, `/profile`, and any non-room-bound
  route fall through to the setup screen.

### Affected files
- `src/pages/AppLayout.tsx` — gating logic.
- (Read-only reference) `src/App.tsx` — route table.
- (Read-only reference) `src/pages/ArchivedProjects.tsx`,
  `src/pages/Profile.tsx` — pages that must work without a room.

### Implementation plan
1. Define a small constant `ROOMLESS_ROUTES` in `AppLayout.tsx`
   (or a sibling helper) listing the pathname prefixes that may
   render without an active room. Initial set:
   - `/archived-projects`
   - `/profile`
2. In the no-active-room branch, check the current `location.pathname`
   against `ROOMLESS_ROUTES`:
   - If it matches → render `<PageTransition>{outlet}</PageTransition>`
     **without** wrapping in `DataProvider` (since `DataProvider`
     requires `roomId`).
   - If it does not match → keep the existing `<ProjectSetup />`
     fallback.
3. Make sure pages in `ROOMLESS_ROUTES` do not assume
   `DataContext` is available. Spot-check
   `ArchivedProjects.tsx` and `Profile.tsx` for `useData()` calls;
   if any exist, fix the page rather than widening the provider.
4. Keep the bottom-nav `activeTab` calculation untouched; tab
   switching from a roomless page back to `/dashboard` will land
   on the setup screen, which is correct.

### Acceptance criteria
- [x] User with no active room can open `/archived-projects` and
      see the archived list (or empty state), not the create/join
      screen.
- [x] User with no active room can open `/profile` and see the
      settings list, not the create/join screen.
- [x] User with no active room visiting `/dashboard`, `/add`,
      `/saving-plan`, `/manage-project`, `/check-balance`,
      `/notifications*` still sees the `ProjectSetup` screen
      (unchanged).
- [x] User with an active room sees no regression on any route.
- [x] Restoring an archived room from `/archived-projects` returns
      the user to a working `/dashboard`.

### Verification notes (2026-05-17)
- `npm run build`: passed (twice — initial commit, and after the
  Profile follow-up below).
- Added `ROOMLESS_ROUTES = ['/archived-projects', '/profile']` and
  an `isRoomlessRoute()` prefix matcher in `src/pages/AppLayout.tsx`.
  No-active-room branch now renders `<PageTransition>{outlet}</PageTransition>`
  without `DataProvider` for those paths; all other paths keep the
  `ProjectSetup` fallback.
- Follow-up after manual test: `Profile.tsx` was calling
  `useSharedData()` (initial grep only looked for `useData(`), which
  threw "useSharedData must be used within DataProvider" when opened
  without an active room. Replaced with a direct `useProfile()` call
  — Profile only consumed `data.profile`, and `useProfile()` is
  room-independent (keyed on auth user). No other roomless page
  touches `DataContext`.

### Verification steps
1. `npm run build` passes.
2. Manually leave the only active room, then:
   - navigate to `/archived-projects` → archived list renders.
   - navigate to `/profile` → settings list renders.
   - navigate to `/dashboard` → setup screen renders.
3. Restore an archived room and confirm `/dashboard` works again.
4. Sign in fresh (no rooms ever created) → `/profile` renders
   normally, `/dashboard` shows setup.

### Risk
- Medium. Touches the app shell render gate; mistakes can hide the
  setup screen for legitimate first-time users or break the
  `DataProvider` contract for room-bound pages.

### Rollback
- Revert `src/pages/AppLayout.tsx`. No SQL, no schema, no data
  changes.

## HOTFIX-002: Daily-increasing plan change saves but does not apply

- **Status**: pending (do NOT start until HOTFIX-001 is approved)
- **Priority**: hotfix
- **Symptom**: On a `increasing_daily` (or `increasing_daily_capped`)
  plan, the user opens "Change plan", picks a new rule type / amounts,
  taps Save. The `change_saving_plan` RPC returns success, the page
  navigates to `/dashboard`, but the active plan rendered on
  Dashboard / Saving Plan is unchanged — the new revision either
  isn't visible or isn't chosen as active.

### Suspected cause (candidates to confirm during implementation)
1. **Wrong effective_from on submit.** `SavingPlan.tsx:462` uses
   `planStartDate || effectiveFromDate` when `ruleType ===
   'increasing_daily'`. `planStartDate` is only seeded by the form
   date picker (default `todayBangkokKey()`); the seeding effect
   (lines 84–114) does **not** reset `planStartDate` from the
   existing revision. If the user opened the form on a prior day
   and the component kept state, or if `planStartDate` drifted to a
   future date via the date picker, the new revision is inserted
   with a future `effective_from_date` and `activeRevisionAt(today)`
   keeps returning the older revision.
2. **Supersede deletes the new row.** Migration 0048 deletes
   revisions where `effective_from_date > v_effective`. If the
   client passes `v_effective = today` but a prior step inserted a
   revision dated tomorrow, that future row is removed — good. But
   if the *new* call's `v_effective` lands earlier than the user's
   most recent revision (e.g. equal-date duplicate at the same
   `created_at` second), `activeRevisionAt` (sorted by
   `effective_from desc, created_at desc`) may still pick the old
   row because of clock skew or PostgREST cached read.
3. **Client cache / stale snapshot.** `useSavingPlan.changePlan`
   calls `fetchPlan()` then resolves. If the Dashboard reads from a
   separate `useSavingPlan` instance (or from `useSharedData`
   composition), it may not see the refetched data before the
   `navigate('/dashboard')` re-mount.
4. **Rule-type seeding mismatch.** The form coerces
   `increasing_daily_capped → increasing_daily` for editing
   (line 90). If the user "changes" to the same `increasing_daily`
   with different amounts, but `change_saving_plan` is called with
   `p_rule_type='increasing_daily'` while the prior revision was
   `increasing_daily_capped`, the *RPC writes correctly* but the
   capped-only fields (`cap_amount`) silently drop — UI may then
   look "unchanged" because the visible summary keeps showing the
   capped variant from the older revision (only true if cause 1/2
   also triggers).

The actual fix must be selected after a short reproduction during
implementation. Most likely cause is **(1)** + **(3)**.

### Affected files
- `src/pages/SavingPlan.tsx` — `effective_from_date` selection on
  submit; `planStartDate` seeding.
- `src/hooks/useSavingPlan.ts` — `changePlan` refetch order,
  optional broadcast to dependent consumers.
- (Read-only reference) `src/lib/savingPlan.ts` —
  `activeRevisionAt` tie-breaking.
- (Read-only reference) `supabase/migrations/0048_relax_change_plan_backdate_guard.sql`
  — current server-side behavior. **Do not edit 0048**; if a SQL
  change is required, add a new migration `0050_*.sql`.

### Implementation plan
1. **Reproduce first.** Add temporary `console.debug` (gated by
   `import.meta.env.DEV`) in `SavingPlan.tsx` `runChange()` and in
   `useSavingPlan.changePlan` to log the outgoing
   `effective_from_date`, the returned `revisionId`, and the
   refetched `plan.revisions[].effective_from_date` after
   `fetchPlan()`. Confirm which of the four causes is firing.
2. **Cause 1 fix.** Reset `planStartDate` to `todayBangkokKey()`
   when entering "change" mode for an existing plan, and clamp
   `effective_from_date` sent to the RPC to today when the chosen
   value is in the past or undesirably in the future for a
   non-increasing rule type. Always send `effective_from_date =
   todayBangkokKey()` for plan changes unless the user explicitly
   picked a future start via the date picker.
3. **Cause 3 fix.** After `changePlan` resolves, await `fetchPlan()`
   *before* `navigate('/dashboard')` in `runChange()` (already done
   inside the hook — verify it's awaited at the call site). If
   Dashboard uses a separate instance, expose a lightweight
   notification (re-use existing `notifyPlanChanged` if available)
   so Dashboard refetches on mount.
4. **Cause 4 fix (only if observed).** When the previous revision
   is `increasing_daily_capped`, surface the capped/un-capped
   choice in the form rather than coercing — or explicitly pass
   `p_rule_type='increasing_daily_capped'` + `p_cap_amount` when
   `capAmount` is present.
5. **Do NOT add a new migration unless reproduction proves the
   server is at fault.** 0048 is recent and intentional.
6. Remove the debug logs before commit.

### Acceptance criteria
- [ ] User on `increasing_daily` who changes to `fixed_daily` sees
      the new rule type reflected on Dashboard and `/saving-plan`
      immediately after save.
- [ ] User on `increasing_daily` who edits only the amounts (still
      `increasing_daily`) sees the new amounts applied immediately.
- [ ] User on `increasing_daily_capped` who edits sees the capped
      rule preserved (no silent drop to non-capped) and the new
      cap/start/increment values applied.
- [ ] No `cannot backdate revision before today` error is raised
      for a same-day change.
- [ ] `savings_logs` are not mutated by this change.
- [ ] No regression on `createPlan`, `pausePlan`, `resumePlan`.

### Verification steps
1. `npm run build` passes; `npm run lint` if practical.
2. Manual reproduction script in a scratch project:
   - Set up `increasing_daily` plan with `start_amount=1`,
     `increment=1`, `target_amount=100000`.
   - Open Change plan, switch to `fixed_daily amount=100`, save.
   - Confirm Dashboard SavingPlanCard now reads "Fixed daily 100"
     and that the latest revision in
     `saving_plan_revisions` has `rule_type='fixed_daily'`,
     `amount=100`, `effective_from_date=today (Bangkok)`.
   - Repeat for `increasing_daily_capped`.
3. SQL spot-check after each save:
   `select rule_type, amount, start_amount, increment_amount,
   cap_amount, effective_from_date, created_at from
   saving_plan_revisions where plan_id = '...' order by
   effective_from_date desc, created_at desc limit 3;`
4. Confirm `activeRevisionAt(revisions, todayBangkokKey())` in a
   quick browser console probe returns the freshly-inserted row.

### Risk
- High. Plan revisions are financial-adjacent state. A wrong
  `effective_from_date` value can hide historical revisions or
  shift the planned amount silently. Migration 0048 already widened
  the guard; further server changes need a fresh migration and
  careful replay analysis.

### Rollback
- Code-only changes: `git revert` the commit.
- If a new migration is added (`0050_*.sql`), roll back via a
  follow-up migration that restores the prior `change_saving_plan`
  body. Never edit 0048 in place.

## Token Discipline / Minimal Context Rule

To save tokens and avoid context bloat:

1. Do not restate the full plan.
2. Do not summarize all tasks after every step.
3. Work only on the current approved task.
4. Read only files directly related to the current task.
5. Do not scan the whole repo unless the task truly requires it.
6. Do not paste large file contents into the response.
7. Report only:
   - task ID
   - what changed
   - files changed
   - checks run
   - commit hash
   - next recommended task
8. Keep status updates short.
9. If blocked, explain the blocker briefly and stop.
10. Do not proactively implement adjacent fixes, even if found.
11. Do not rewrite the entire plan document after each task.
    Only update the current task status, verification notes, and final checklist if needed.
12. Prefer targeted diffs over broad refactors.
13. Do not repeat unchanged acceptance criteria in chat.

## Repo Findings

### Framework & routing
- React 19 + TypeScript + Vite 5, PWA via `vite-plugin-pwa`.
- React Router 6 at `src/App.tsx` with routes:
  `/dashboard`, `/add`, `/check-balance`, `/saving-plan`,
  `/manage-project`, `/notifications`, `/notifications/settings`,
  `/profile`, plus auth callback and preview routes (Atoms/Molecules/
  Organisms preview pages live behind feature toggles, no UI trace).
- Custom `PageTransition` (`src/components/PageTransition/PageTransition.tsx`)
  uses `framer-motion` with direction-aware spring transitions and a
  per-history index snapshot.
- App shell is `src/pages/AppLayout.tsx`; it renders a sticky bottom
  nav, the project-setup gate, and the `<Outlet />`.

### State / data fetching
- No external data library (no React Query / SWR). Data lives in
  `src/hooks/use*.ts` files plus `useSharedData()`
  (`src/hooks/useSharedData.ts`) which composes profile, room, goal,
  logs, buckets, reconcile, saving plan, leaderboard, partner buckets.
- Supabase singleton at `src/lib/supabase.ts` — every read/write goes
  through this client (CLAUDE.md hard rule).
- Several hooks register a `window 'focus'` listener for refetch
  (`useNotifications`, `useUnreadNotificationsCount`).
- PWA SW lifecycle is bound in `src/lib/pwaUpdate.ts`. A
  `visibilitychange` handler on the registration triggers
  `registration.update()`, and `onNeedReload` calls
  `window.location.reload()` once per `appVersion()` via
  `pwaReloadedForVersion` in `sessionStorage`.

### Notification architecture
- In-app: `notifications` table + `notificationDisplayCopy()` in
  `src/i18n/notificationCopy.ts` localizes via the `event_key` and
  the stored `payload`.
- Push: `src/sw.ts` handles `'push'` and `'notificationclick'`. It
  prefers an existing focused client on the target route, else opens
  the SPA at the deep link.
- Subscription handling: `src/hooks/usePushSubscription.ts`,
  `notification_preferences` row gated by
  `master_enabled / push_enabled / nudges_enabled /
  saving_reminders_enabled`.
- Server-side senders:
  - `supabase/functions/send-nudge/index.ts` — manual nudges.
  - `supabase/functions/scheduled-saving-reminders/index.ts` — cron
    style sweep that calls `enqueue_saving_plan_reminders()` RPC
    (migration `0039`) then pushes for each enqueued row.
  - Partner events are enqueued by RPCs in migration `0040`
    (`notify_partner_deposit`, `notify_balance_checked`,
    `notify_plan_*`).

### i18n / localization architecture
- Provider: `src/i18n/I18nProvider.tsx`. Language is read from a
  storage key plus `profile.language` (synced via
  `ProfileLanguageSync` in `AppLayout`).
- Languages: `en` (default) and `th`. Native labels in
  `src/i18n/languages.ts`.
- Copy lives in `src/i18n/locales/en.ts` and `src/i18n/locales/th.ts`,

- Push payload titles/bodies for partner events (in SQL) and the

### Plan / revision data model

### P0-001: Fix deposit reminder push notifications (daily / daily-increasing)
- Status: done
- Priority: P0
- Original feedback: *"user doesn't get notifications about remind to deposit money even their plan is daily increasing plan or daily plan."*
- Product requirement: A user with an active `daily` or
  `daily_increasing` (and capped variants) saving plan must receive
  one push per day in the configured reminder window if they have not
  already deposited that day.
- Repo findings:
  - `enqueue_saving_plan_reminders()` in
    `supabase/migrations/0039_saving_reminder_notifications.sql`
    gates by `master_enabled AND saving_reminders_enabled` and skips
    users who already deposited today (Bangkok). It also gates by
    `now() in Asia/Bangkok >= 18:00` (line ~70). Plan-type filter is
    `rule_type IN ('daily', 'daily_increasing')`.
  - The edge wrapper `scheduled-saving-reminders/index.ts` calls the
    RPC, then iterates `push_subscriptions` and sends Web Push.
  - Pause rows from `saving_plan_pauses` are excluded.
- Suspected cause: candidates to confirm during inspection in
  implementation phase:
  1. `rule_type` filter omits the capped variants added in
     `0032_saving_plan_capped_increasing.sql` /
     `0033_saving_plan_capped_day_count_required.sql` /
     `0034_saving_plan_capped_day_count_optional.sql`, so users on
     "daily increasing" capped plans are excluded.
  2. The 18:00 Bangkok cutoff plus cron cadence may skip the window
     entirely.
  3. Deposit-of-the-day detection may use UTC instead of Bangkok.
  4. Missing `notification_preferences` row defaults could short
     circuit the join.
- Implementation plan:
  1. Read the RPC end-to-end and confirm which `rule_type` values
     exist in `saving_plan_revisions` after `0034`.
  2. Add a new migration `0046_fix_saving_reminder_eligibility.sql`
     that:
     - widens the `rule_type` filter to all daily-style rule types,
     - normalizes "deposit today" to Bangkok date using the existing
       helper (`current_bangkok_date()` style if present, else
       `(now() at time zone 'Asia/Bangkok')::date`),
     - upserts default `notification_preferences` to `true` defaults
       so missing rows do not exclude the user.
  3. Audit `scheduled-saving-reminders/index.ts` for:
     - timezone-correct cron timing,
     - logging of skipped users so we can debug,
     - Thai title/body selection (P2-004 will go further; here we
       just ensure the title falls back via the language column).
  4. Add structured `console.warn` lines for each skip reason in the
     edge function (read-only debug, no behavior change).
- Acceptance criteria:
  - [ ] User with `daily` rule type and no deposit today receives a
        push after 18:00 Bangkok.
  - [ ] User with `daily_increasing` (and capped variants) rule type
        receives a push.
  - [ ] User who already deposited today does not get a duplicate.
  - [ ] User who paused the plan does not get a push.
  - [ ] User with `master_enabled=false` or
        `saving_reminders_enabled=false` does not get a push.
  - [ ] Skips are logged.
- Regression test plan: SQL trace runs of
  `enqueue_saving_plan_reminders()` against test rooms covering the
  five scenarios; manual push trigger via edge function `--no-verify`
  invocation.
- Verification notes:
  - Confirmed all five existing `rule_type` values
    (`fixed_daily`, `fixed_weekly`, `fixed_monthly`,
    `increasing_daily`, `increasing_daily_capped`) reach `daily` /
    `weekly` / `monthly` cadence in the rebuilt RPC.
  - Confirmed Bangkok-date deposit-of-the-day check already uses
    `(s.created_at at time zone 'Asia/Bangkok')::date`; no UTC bug.
  - Confirmed migration `0037` set
    `notification_preferences.saving_reminders_enabled` default to
    `false`; combined with `get_notification_preferences` auto-insert
    of a defaults-only row, every existing user was effectively
    opted-OUT — root cause.
  - Migration `0046_fix_saving_reminder_eligibility.sql`:
    flips column default to `true`, backfills only untouched rows
    (`updated_at = created_at`) so explicit user opt-outs survive,
    and rebuilds the RPC with `coalesce(prefs.saving_reminders_enabled, true)`
    plus an explicit `rule_type` whitelist.
  - Edge function: added `console.warn` lines on
    `push_disabled` / `no_devices` skip paths and an `enqueue
    created=… recipients=…` summary `console.info` line, so future
    debugging can read why a recipient was skipped from Supabase
    logs.
  - `npm run build` (`tsc -b && vite build`): passed.
- Risk level: medium (cron behavior, RPC change is additive).
- Rollback notes: revert the new `0046_*.sql` migration by adding a
  follow-up migration that recreates the prior function body
  (do **not** edit `0039`). Code-level changes in the edge function

### P0-002: Fix incorrect nudge notification failure UI
- Status: done
- Priority: P0
- Original feedback: *"user tap on nudge but ui said 'can't notifications saved for "user name" but push couldn't delivered'. However i got notification pushed from my friend."*
- Product requirement: When a nudge results in at least one delivered
  push, the sender must see success copy. The "saved but push not
  delivered" copy must only appear when zero pushes are delivered.
- Repo findings:
  - `NudgeButton.tsx` maps `response.status` to UI via
    `messageForStatus`. Statuses come from `send-nudge` edge
    function: `'sent' | 'saved_no_push' | 'throttled'`.
  - Edge function sets `status = delivered > 0 ? 'sent' :
    'saved_no_push'` and *always* attaches an `error` field when
    `delivered === 0` (line ~382). Note: `error` is set for both
    `saved_no_push` and `throttled` responses.
  - In `NudgeButton.tsx` the `default` branch in `messageForStatus`
    returns `response.error ?? n.sent(partner)`. If `status` is
    missing but `error` is present (e.g. `throttled` HTTP 429 returns
    an `error` field), this default branch fires.
  - Successful `'sent'` response shape is `{status: 'sent', delivered,
    notification_id}` with no `error`, so success path is fine.
- Suspected cause: the edge function sometimes returns `status:
  'saved_no_push'` for nudges where push *was* delivered to a second
  device after the first failed with 410. Alternatively, the client
  treats a `data.error` as failure even when `status === 'sent'`.
  Need to inspect actual response on the failing case.
- Implementation plan:
  1. Adjust `messageForStatus` so `'sent'` is always treated as
     success regardless of any auxiliary `error` field.
  2. Confirm edge function only attaches `error` when `delivered === 0`
     (already true per current code), but consider stripping the
     `error` field on `'sent'` defensively.
  3. Improve copy in `n.notifications.nudge`:
     - `sent` (delivered > 0): "Nudge sent to {partner}".
     - `savedNoPush` (delivered === 0): "Saved nudge for {partner}.
       Push could not be delivered."
     - `throttled` / `throttledGeneric`: keep existing.
  4. Make sure Thai copy in `i18n/locales/th.ts` matches the new
     phrasing and is natural ("ส่งสะกิดถึง …" / "บันทึกการสะกิดของ
     …" / "รอสักครู่ก่อนสะกิดอีกครั้ง").
  5. Add a defensive log of the response shape behind
     `import.meta.env.DEV` to aid future debugging.
- Acceptance criteria:
  - [ ] When push delivers, UI shows success copy with no error
        suffix.
  - [ ] When push fails entirely, UI shows the saved-only copy.
  - [ ] Throttled response shows the throttled copy.
  - [ ] Thai copy is natural and consistent.
- Regression test plan: manual click with three mocked edge responses
  (sent / saved_no_push / throttled) via temporary `console.log`.
- Verification notes:
  - Root cause confirmed in `messageForStatus`: the `default` branch
    returned `response.error ?? n.sent(partner)`. The `send-nudge` edge
    function only attaches `error` when `delivered === 0`, but if the
    server response shape ever lacked `status` (e.g. on a partial
    deploy or older client cache hitting newer payload), the fallback
    surfaced the "Push could not be delivered" copy even when the
    partner's device received the push through an earlier delivery
    attempt or duplicate dedupe.
  - Fix: `default` branch now picks success copy whenever
    `delivered > 0`, else the saved-only copy — never `response.error`.
    The `'sent' / 'throttled' / 'saved_no_push'` switch arms are
    unchanged so the recognized paths behave as before.
  - Added a `import.meta.env.DEV`-gated `console.debug` of the raw
    response shape to aid future field debugging.
  - Edge function `send-nudge/index.ts` already strips `error` when
    `delivered > 0` (line ~382), so no server-side change was needed.
  - Thai/English copy keys (`n.sent` / `n.savedNoPush` /
    `n.throttledGeneric`) already exist and read naturally; no i18n
    changes required.
  - `npm run build` (`tsc -b && vite build`): passed.
- Risk level: low.
- Rollback notes: revert the single component change; no SQL.
